# Migration history gap

This directory captures migrations going forward. It does **not** yet contain the 3 migrations
that built the current live schema, applied directly to the remote project before this file
existed:

- `20260730181201_init_commerce_schema`
- `20260730181213_payment_slips_bucket`
- `20260730185111_harden_rls_and_atomic_order_creation`

Their exact SQL was not reconstructed here — only introspected end-state was available (via
`list_tables`/`execute_sql`), and hand-writing migration files that *claim* to reproduce
history I can't verify would risk silently diverging from the real DDL (trigger bodies, grants,
etc.) if anyone ever ran `supabase db reset` against them.

## Correction (2026-08-01, Foundation Artifact Preservation pass)

The paragraph that previously stood here claimed `supabase db pull` would "backfill the 3
migrations above as real files from the actual remote history." **That overstates what `db pull`
does and is corrected below.**

**What `supabase db pull` actually produces:** a schema diff between the remote database's current
end state and the local migration history, written out as one or more new migration files. It is a
**baseline of the current remote schema**, generated by introspecting live objects — not a retrieval
of the original SQL text that was actually executed to create those objects historically. Supabase
does not store or expose the original DDL statements for migrations applied outside the CLI's own
migration-tracking table; `db pull` cannot recover text that was never captured.

**What this means concretely for the 3 uncaptured migrations above:**

1. The exact original SQL bodies of `20260730181201_init_commerce_schema`,
   `20260730181213_payment_slips_bucket`, and `20260730185111_harden_rls_and_atomic_order_creation`
   are **not available locally and cannot be recovered** by running `db pull`.
2. A `db pull` run today would instead produce a **baseline migration representing the schema's
   current state** — tables, columns, and constraints as they exist right now, not as three
   discrete historical steps.
3. **A generated baseline is not proof that it is the exact original source of those three
   migrations.** Two schemas can converge to the same end state via different DDL (different
   constraint names, different trigger definitions with equivalent behavior, different grant
   ordering) — a `db pull` diff records only the destination, not the path taken to it.
4. Before this baseline is trusted for any purpose (including `supabase db reset`), it must be
   manually reviewed against what is independently already known about the live schema (see
   `docs/supabase-migration/03-data-model-inventory.md` and
   `docs/supabase-migration/12-rls-and-authorization-audit.md`), covering at minimum:
   - Tables and columns
   - Constraints (check constraints, foreign keys, uniqueness)
   - Functions (including `private.*` and any `SECURITY DEFINER` functions)
   - Triggers
   - RLS policies
   - Grants (table-level and column-level)
   - Objects in the `private` schema
   - Storage policies (RLS policies on `storage.objects`, not just the bucket row)
   - Any customizations to the `auth` schema
5. **Custom Auth and Storage objects may not be captured by a plain schema pull at all.**
   Auth-schema customizations and storage policies can require schema-specific capture steps or
   explicit hand-written migrations — a generic `db pull` targeting `public`/`private` should not be
   assumed to have captured these without independent verification.
6. **A schema baseline alone does not represent Storage bucket configuration.** Bucket rows
   (`storage.buckets`) carry configuration — privacy (public/private), file-size limits, and
   allowed MIME types — that is data, not DDL, and is not guaranteed to be reproduced by a schema
   migration. If the `payment-slips` bucket's configuration needs to be reproducible, it must be
   captured and verified intentionally (e.g., a documented `insert`/`update` against
   `storage.buckets` with the exact intended values), not assumed to fall out of `db pull`.
7. **Do not trust `supabase db reset` to fully reproduce the current remote Supabase project's
   schema until the baseline above has been generated, reviewed, and verified locally** — running
   `db reset` against an incomplete or unverified baseline will produce a local database that
   silently diverges from the remote one in ways items 4-6 describe, which would undermine every
   pgTAP test that depends on the schema matching.

This document intentionally refers to **"the current remote Supabase project,"** not "production."
Environment classification remains **Development Candidate — Awaiting User Confirmation**
(`docs/supabase-migration/13-environment-classification.md`); calling it "production" here would
overstate a classification that has not been confirmed by the user.

`20260731174520_add_profiles_foundation.sql` and `20260731174630_revoke_anon_grants_on_profiles.sql`
(both from a later pass) remain safe as-is: each was applied via `apply_migration` and its file here
is an exact copy of what was executed — this is a materially different provenance than a `db pull`
baseline, since these two were captured as their own original migration text, not reconstructed from
end-state introspection.

## Correction (2026-08-01, Migration-Baseline Reconciliation pass)

The gap described above is now closed with three new files:

- `20260730181201_remote_history_marker.sql` — no-op. Occupies a remote-verified timestamp whose
  original SQL was not recovered. Contains no DDL.
- `20260730181213_remote_history_marker.sql` — no-op, same reasoning.
- `20260730185111_baseline_remote_schema.sql` — reconstructs the verified combined remote end
  state spanning all three missing timestamps (private schema, `orders`/`products`/`settings`
  tables, their constraints/indexes/triggers/RLS/policies, `private.set_updated_at()`,
  `private.is_admin()`, `public.create_order()`, `public.rls_auto_enable()` and its event trigger).

None of these three files claim to reproduce the original three-step DDL history: attribution of
any individual object to one specific original migration (`init_commerce_schema` /
`payment_slips_bucket` / `harden_rls_and_atomic_order_creation`) is unknown and is not claimed.
Each file's own header comment repeats this in full. See
`docs/supabase-migration/` reconciliation evidence and the accompanying evidence-package matrix
(`17-reconciliation-matrix.md`, outside this repository) for the complete object-by-object
sourcing. This correction does not change the "Development Candidate — Awaiting User
Confirmation" environment classification.

The `payment-slips` storage bucket (data, not schema DDL) remains reproduced separately via
`[storage.buckets.payment-slips]` in `supabase/config.toml`, per the prior correction above — not
part of these three migration files.
