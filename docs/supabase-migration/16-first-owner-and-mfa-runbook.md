# 16 — First Owner and MFA Runbook

Procedural documentation only. No user was created, no password was generated, and no
`app_metadata` was set on any real account during this pass — creating an administrator on the
live project is a remote, consequential action requiring explicit user approval per this task's
safety rules, and this project's environment classification is not yet fully confirmed by the user
(see 13-environment-classification.md — Production is ruled out by evidence, Development is
recommended but unconfirmed).

This runbook documents the procedure to follow when the user is ready to execute it themselves (or
explicitly asks this agent to execute specific steps against a confirmed-safe project).

## 1. Create the first Auth user through a secure approved method

Do **not** insert directly into `auth.users` via SQL for a real account — that bypasses Supabase
Auth's password hashing, email-confirmation flow, and session machinery, and is only appropriate
for disposable pgTAP test fixtures (see `supabase/tests/*.test.sql`) or `supabase/seed.sql` in a
local stack.

Approved methods, in order of preference:
- **Supabase Dashboard → Authentication → Users → Add user**, with a strong, unique password the
  owner generates and stores in their own password manager (never shared with or generated by this
  agent).
- The application's own sign-up flow, if/when one exists for authenticated (non-guest) accounts —
  not currently built (see 09-foundation-decisions.md, guest-checkout decision).
- `supabase.auth.admin.createUser()` via the `service_role` key, run from a trusted, non-browser
  context only (e.g., a one-off local script the owner runs themselves) — never from client code,
  never with the `service_role` key present in any `VITE_`-prefixed variable.

## 2. Verify the email

Use the dashboard's built-in confirmation toggle, or complete the standard email-confirmation link
flow if the project has email sending configured. An unconfirmed admin account should not be relied
upon for production access.

## 3. Set `app_metadata.role = 'admin'` using a server-authorized method

`app_metadata` cannot be set by the user themselves (see verification in step 4). It must be set
by:
- The Supabase Dashboard's user-edit UI (which itself calls the Auth admin API under the hood), or
- `supabase.auth.admin.updateUserById(userId, { app_metadata: { role: 'admin' } })` using the
  `service_role` key from a trusted context.

This is the **only** authorization signal this project currently trusts — confirmed as the single
source of truth with no drift in 12-rls-and-authorization-audit.md. Setting it incorrectly (e.g., a
typo, or using `user_metadata` instead of `app_metadata`) will silently fail to grant access rather
than error, since `private.is_admin()` simply evaluates to `false` for anything that doesn't match.

### Correction (2026-08-01, Foundation Evidence Reconciliation pass) — JWT freshness, not documented before

Updating `app_metadata.role` changes the *database record* for that user immediately, but does
**not** necessarily change what an already-issued access token claims. Supabase Auth access tokens
are JWTs — the claims inside are fixed at the moment the token was minted (sign-in, or the last
token refresh) and are not re-read from the database on every request. Concretely:

1. If the admin (or an attacker who briefly held admin) already has a valid access token containing
   `app_metadata.role = 'admin'`, revoking the role in the database does **not** invalidate that
   token — it remains valid, and any RLS policy checking `auth.jwt() -> 'app_metadata' ->> 'role'`
   will still see `'admin'` in it, until the token expires or the client refreshes its session
   (which re-fetches current claims from the Auth server).
2. **Immediate removal requires session revocation, not just an `app_metadata` change.** If an
   admin must lose access *right now* (compromise response, offboarding with immediate effect), the
   `app_metadata` change must be paired with revoking that user's active sessions via the Auth admin
   API (or dashboard equivalent), not relied on alone.
3. Changing `app_metadata` alone is therefore **insufficient** for immediate revocation — it is
   correct and sufficient for *new* sign-ins and for sessions once they refresh, but not for a
   currently-live session holding an old token.
4. Every admin-gated RLS policy in this project reads `auth.jwt()` (12-rls-and-authorization-audit.md)
   — meaning they see claims **from the token the client presents on that request**, not a live
   database lookup. This is standard, correct Supabase JWT-based authorization behavior, not a
   defect in this project's policies — but it means "I changed `app_metadata`" and "that user's
   access is gone right now" are two different claims, and this runbook previously did not
   distinguish them.

This directly updates step 13 (offboarding) and step 14 (compromised-account response) below —
both now explicitly require a session-revocation step, not `app_metadata` alone.

## 4. Confirm normal users cannot set `app_metadata`

Verified this pass (see `supabase/tests/authorization_is_admin.test.sql`, test 5, and directly via
`information_schema.role_table_grants`): neither `anon` nor `authenticated` holds any `UPDATE`
grant on `auth.users` at all. `app_metadata` is exclusively writable by `service_role`/the Auth
admin API, never by a client session. This is a platform-level guarantee, not something this
repository's code independently enforces or could accidentally weaken.

## 5. Log in to the administrator UI

Sign in at the app's normal auth entry point using the credentials from step 1. Confirm
`AdminPage.tsx`'s `isAdminSession` check (`session.user.app_metadata?.role === 'admin'`) resolves
to `true` and the admin dashboard renders.

## 6. MFA — corrected 2026-08-01 and split into distinct steps

**Do not claim MFA is enforced today.** No restrictive RLS policy or application logic in this
project currently requires `aal2` for anything — every admin-gated RLS policy checks
`app_metadata.role` only (12-rls-and-authorization-audit.md). MFA enrollment, if performed, is
currently a purely optional, self-selected control with no policy consuming it. The steps below are
kept separate deliberately, per this task's own instruction, because "MFA enrolled" and "MFA
enforced" are different claims and were previously blurred into one step.

### 6a. MFA enrollment

Use Supabase Auth's MFA enrollment flow (`supabase.auth.mfa.enroll()`, TOTP factor) from the
signed-in admin session. This project's frontend does not currently have a built MFA-enrollment UI
— **[Unverified]** whether one exists; not found in the files reviewed this pass. Enrolling via the
Supabase client SDK directly (e.g., a short authenticated script, or the Supabase Dashboard's own
"Sign in as user" tooling if available) is the fallback until a dedicated UI is built. Building that
UI is out of scope for this foundation-closure/reconciliation task.

### 6b. MFA challenge

After enrollment, a subsequent sign-in (or an explicit step-up) must call
`supabase.auth.mfa.challenge()` followed by `supabase.auth.mfa.verify()` with the TOTP code to
actually elevate the session's assurance level. Enrollment alone does not raise the current
session's `aal` — a session that predates enrollment, or one that never completed a challenge,
remains at `aal1` even if the user has an enrolled factor.

### 6c. Verifying assurance level — corrected method

**Do not instruct the user to rely on `getSession().session.aal`** unless direct inspection of the
installed `@supabase/supabase-js` version proves that field exists and is the currently-supported
way to read it — this was not verified this pass, and per this project's own skill guidance
("Supabase changes frequently — verify against current docs before implementing"), assuming a
specific session-object shape from training data is exactly the kind of claim that needs a fresh
check at implementation time. The documented, supported JavaScript API for this is:

```ts
const { data, error } =
  await supabase.auth.mfa.getAuthenticatorAssuranceLevel()

const { currentLevel, nextLevel } = data
```

`currentLevel` reflects the session's actual assurance level (`aal1` or `aal2`); `nextLevel`
indicates whether a step-up is available/required. Use this function, not an assumed field on the
session object, when this is implemented.

### 6d. RLS enforcement for high-risk operations

No RLS policy in this project currently checks assurance level at all (verified,
12-rls-and-authorization-audit.md — every admin policy's sole condition is `private.is_admin()`).
If MFA is ever meant to gate a specific high-risk operation (e.g., destructive admin actions,
`service_role`-adjacent operations), that would require a new policy condition reading the assurance
claim from `auth.jwt()` (the exact claim path was not verified this pass — needs re-confirmation
against current Supabase Auth docs before implementation) in addition to `private.is_admin()`, not
instead of it. Not designed here — this is a future decision, not a current implementation.

### 6e. UI redirection for an `aal1` administrator

If MFA enforcement is ever added, the frontend would need to detect an admin session at `aal1` (via
6c above) and redirect to a step-up/challenge flow before rendering privileged UI, mirroring the
existing `isAdminSession` gate pattern in `AdminPage.tsx`. **[Unverified]/not built** — no such
redirect exists in the files reviewed this pass.

### 6f. Recovery-code / lost-factor procedure

**[Unverified] / not yet decided.** No documented procedure exists in this repository for an admin

### 6g. Administrator session revocation

Distinct from MFA itself, but directly relevant to it: forcing an admin to re-authenticate (e.g.,
after enrolling MFA for the first time, or after a suspected compromise) requires revoking that
user's existing sessions via the Auth admin API — see the correction under step 3 above. Enrolling
a new factor does not retroactively invalidate sessions that were already at `aal1`.

## 10. Test logout

Confirm `supabase.auth.signOut()` invalidates the local session and that a subsequent request using
the old access token is rejected once it expires. Note the platform limitation already documented
in 05-security-findings.md: deleting a user does not retroactively invalidate a still-valid access
token already issued — sign-out/token-expiry are the actual controls, not user deletion.

## 11. Test session expiry

Confirm the configured JWT expiry (Supabase project auth settings, not found/reviewed in this
repository — dashboard-only configuration) behaves as expected: an expired access token is rejected
and a refresh token successfully mints a new one, or is itself expired/revoked as configured.

## 13. Document administrator offboarding

**[Unverified] / not yet decided.** **Corrected 2026-08-01** (see the JWT-freshness correction under
step 3): the previous wording here claimed setting `app_metadata.role` away from `'admin'` is "an
instant, authoritative revocation since `private.is_admin()` re-evaluates the JWT claim on every
check." That is wrong — `private.is_admin()` evaluates the claim **inside the token the client
presents**, and that token's claims do not change until the token expires or the session refreshes.
Recommended minimum procedure, corrected:
(a) set `app_metadata.role` to something other than `'admin'` (correct for all *future* sign-ins and
for any session once it refreshes, but does **not** by itself end an already-active session), (b)
**if immediate removal is required**, additionally revoke the user's active sessions via the Auth
admin API/dashboard — this is the step that actually ends current access, not (a) alone, (c)
disable or delete the Auth user depending on retention policy, (d) rotate any shared secrets the
offboarded admin had access to (`service_role` key, database password, `SUPABASE_ACCESS_TOKEN`) if
they had direct project access beyond the application.

## 14. Document compromised-account response

**[Unverified] / not yet decided.** **Corrected 2026-08-01:** recommended minimum procedure, in
order, with the session-revocation step now explicit rather than implied: (a) immediately set
`app_metadata.role` away from `'admin'` (stops new admin-privileged sign-ins/refreshes, does not by
itself end an already-live session — see step 3's correction), (b) **immediately force sign-out of
all sessions for that user** via the Supabase Auth admin API (this is the step that actually ends
the attacker's/compromised session's current access — (a) alone is insufficient, per the JWT-
freshness correction above), (c) rotate the account's password, (d) audit `orders`/`products`/
`settings` for unauthorized changes made during the compromise window (no `audit` schema currently
exists to make this straightforward — see 09-foundation-decisions.md and
10-foundation-verification.md; this is a real, standing gap this runbook cannot resolve on its
own), (e) review Supabase Auth logs for the account's session history.
